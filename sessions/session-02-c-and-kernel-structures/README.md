# Session 02：C 与内核数据结构

## 目标

这一节不是去背一套孤立的 C 语言知识点，而是补齐“能读内核驱动源码”所必须的阅读基础。学完之后，你应该不再把 `struct`、函数指针、链表、锁、对象嵌入看成零散语法，而是能把它们理解成驱动里组织状态、行为和生命周期的方式。

- 理解驱动源码里最常见的对象组织方式。
- 看懂 `struct` 嵌套、对象嵌入、函数指针表和链表这几类模式。
- 知道为什么内核代码大量使用 `container_of`、`list_head`、`ops` table。
- 为后面的 `DRM/KMS`、`ioctl`、buffer 对象、调度和同步打好阅读基础。

## 核心问题

- 为什么内核驱动这么喜欢用“大结构体 + 嵌入式成员”的写法？
- `container_of` 到底在解决什么问题，为什么它几乎无处不在？
- `list_head`、回调函数、`ops` table、引用计数、锁这些模式分别承担什么职责？
- 当你读一个 GPU 驱动对象时，应该先看哪些字段，怎么判断它和别的对象是什么关系？

## 学习内容

### 1. 为什么第二节先补 C 与内核数据结构

很多人看 GPU 驱动源码卡住，并不是一开始就卡在图形学、调度器或者显存管理，而是先卡在代码的“写法”上。

例如你会反复看到这些东西：

- 一个结构体里嵌着另一个结构体。
- 传进来的参数只是一个 `list_head *`，但代码却能还原出完整对象。
- 同一类对象看起来共享一套函数表，比如 `ops`、`funcs`、`helper_funcs`。
- 逻辑里没有“类”，但又明显有“继承感”和“多态感”。
- 很多字段不是业务数据，而是锁、引用计数、链表节点、工作队列、状态位。

如果这些模式没看顺，后面读 `drm_device`、`drm_crtc`、`drm_plane`、`dma_fence`、`amdgpu_bo`、`i915_request` 的时候会一直觉得“每一行都认识，但合起来看不懂”。

所以这一节的重点不是刷语法题，而是建立一种源码阅读视角：

- 这个结构体代表什么对象。
- 它嵌入了哪些公共基类式成员。
- 它通过哪些链表或树挂进全局管理。
- 它的行为是通过哪些 `ops`/回调接出去的。
- 它的并发和生命周期由什么机制保护。

### 2. 先把“内核对象”想成什么

在用户态教程里，大家常常把结构体看成“几个字段打包在一起”。但在内核和驱动里，结构体更像一个对象实例，它通常同时包含下面几类信息：

- 身份信息：这个对象是谁，比如 id、名字、类型。
- 资源信息：它持有哪些内存、寄存器、buffer、引用。
- 关系信息：它挂在哪个链表里，父子对象是谁。
- 行为入口：它能做什么，对应哪些函数指针或 `ops`。
- 同步手段：谁能并发访问，靠什么锁保护。
- 生命周期状态：是否初始化、是否注册、是否销毁中、引用是否归零。

也就是说，内核结构体往往不是“数据容器”，而是“对象全貌”。

后面你在 GPU 驱动里看到一个大结构体时，不要先害怕字段多。先问自己：

- 哪些字段描述对象本身？
- 哪些字段是挂接到框架里的“接口位”？
- 哪些字段是并发控制和生命周期控制？

把字段先按角色分组，阅读难度会立刻下降很多。

### 3. `struct` 不只是“打包数据”，而是对象建模工具

驱动代码里最常见的模式是“大对象里嵌小对象”。

例如可以先抽象成下面这种形式：

```c
struct drm_device {
    struct device *dev;
    const struct file_operations *fops;
    struct mutex mode_config_mutex;
};

struct my_gpu_device {
    struct drm_device drm;
    void __iomem *mmio;
    struct list_head bo_list;
    spinlock_t irq_lock;
};
```

这里 `my_gpu_device` 不是“包含一个完全无关的 `drm_device`”，而是在说：

- 这是一个具体 GPU 驱动对象。
- 它要接入 DRM 公共框架。
- 所以它把 `drm_device` 这一层公共能力嵌进自己内部。

这个写法非常重要，因为它让“框架公共部分”和“驱动私有部分”自然拼在一起。

你可以先记一个阅读习惯：

- 结构体开头那些来自框架的成员，通常决定它怎样接进公共子系统。
- 后面那些私有字段，通常决定它怎样驱动具体硬件。

### 4. 什么叫对象嵌入，为什么内核爱这么干

内核里没有 C++ 那种类继承机制，但经常用“结构体嵌入”实现类似效果。

最常见的形式有两种：

1. 把公共对象当成员嵌进去。
2. 把用于挂接框架的节点嵌进去。

比如：

```c
struct my_buffer {
    struct drm_gem_object base;
    struct list_head lru_node;
    struct kref refcount;
    size_t size;
};
```

这几行分别表达的是：

- `base`：这是一个基于 `drm_gem_object` 扩展出来的具体 buffer 对象。
- `lru_node`：它可以被挂进某个 LRU 链表。
- `refcount`：它有独立引用计数。
- `size`：这是它自己的私有属性。

所以嵌入不是“代码风格偏好”，而是一种对象建模手段：

- 通过嵌入公共对象接入公共框架。
- 通过嵌入链表节点接入某个对象集合。
- 通过嵌入锁和引用计数让对象自带并发和生命周期控制。

### 5. `container_of` 到底在做什么，以及它是怎么实现的

当你只拿到某个成员的地址，但真正想要的是“这个成员属于哪个完整对象”时，就要用 `container_of`。

它解决的是一个非常核心的问题：

- 很多通用框架只认识“公共成员”或“链表节点”。
- 但驱动代码最终想拿回“具体私有对象”。

典型场景就是链表遍历。

```c
struct my_buffer {
    struct list_head node;
    int id;
};
```

如果某个函数只拿到 `struct list_head *node`，它怎么知道这是哪个 `my_buffer`？

答案就是：通过成员在结构体里的偏移量，反推出整个结构体的首地址。

概念上可以这么理解：

```c
obj_addr = member_addr - offset_of(type, member)
```

于是：

- 框架层可以统一操作链表节点、基类节点、回调节点。
- 驱动层可以在需要时还原出自己的完整对象。

所以 `container_of` 本质上是在打通“通用接口视角”和“具体对象视角”。

只讲概念还不够，因为后面你在内核里会真的看到它的宏实现。可以先看一个经典版本：

```c
#define container_of(ptr, type, member) ({                      \
    const typeof(((type *)0)->member) *__mptr = (ptr);         \
    (type *)((char *)__mptr - offsetof(type, member));         \
})
```

这段代码第一次看很绕，但本质只做三件事。

第一件事：先把传进来的成员指针保存下来。

```c
const typeof(((type *)0)->member) *__mptr = (ptr);
```

这里的重点不是空指针，而是“拿到成员类型”。

- `type` 是完整结构体类型，比如 `struct my_buffer`
- `member` 是成员名，比如 `node`
- `((type *)0)->member` 只是为了得到这个成员的类型，不是真的去访问地址 0
- `typeof(...)` 因此能推导出 `member` 的真实类型

这一行的作用可以简单理解成：

- 把传进来的 `ptr` 先当成“这个成员类型的指针”保存起来
- 顺便让编译器帮你做一层类型约束

第二件事：计算这个成员在完整结构体里的偏移量。

```c
offsetof(type, member)
```

例如：

```c
struct my_buffer {
    int id;
    int size;
    struct list_head node;
};
```

如果 `node` 在这个结构体里的偏移是 8 字节，那么：

```c
offsetof(struct my_buffer, node) == 8
```

第三件事：用“成员地址减偏移量”还原出完整对象地址。

```c
(type *)((char *)__mptr - offsetof(type, member))
```

这里为什么先转成 `char *` 很关键，因为：

- `char *` 的指针运算按字节进行
- 而我们现在需要减去的是“字节偏移量”，不是“若干个结构体单位”

所以这一步本质上就是：

```c
完整对象地址 = 成员地址 - 成员偏移
```

可以把它画成这样：

```text
struct my_buffer buf

0x1000  id
0x1004  size
0x1008  node
```

如果你手里只有：

```c
struct list_head *p = &buf.node;
```

那么：

- `p` 的值是 `0x1008`
- `offsetof(struct my_buffer, node)` 是 `8`

于是：

```text
0x1008 - 8 = 0x1000
```

就回到了 `buf` 本身。

所以你可以把 `container_of` 永远记成一句公式：

```c
container = member_ptr - offset(member in container)
```

这也是为什么它和侵入式链表天生是一对。链表代码通常只拿到 `list_head *`，但驱动真正要操作的是完整对象，于是就需要：

```c
struct my_buffer *buf;
buf = container_of(node_ptr, struct my_buffer, node);
```

现代内核里的 `container_of` 实现会比这个例子更严格一些，常常会再加类型检查和编译期保护，但核心思想完全没变：

- 确认 `ptr` 是某个成员的指针
- 算出这个成员在结构体里的偏移
- 从成员地址退回到完整对象地址

### 6. 为什么链表在内核里到处都是

内核经常使用侵入式链表，也就是把链表节点直接放进对象内部，而不是单独分配一个链表包装节点。

最典型的形式就是：

```c
struct list_head {
    struct list_head *next;
    struct list_head *prev;
};
```

然后对象里嵌一个成员：

```c
struct my_request {
    struct list_head link;
    int seqno;
};
```

这样设计有几个好处：

- 不需要为“链表节点外壳”额外分配内存。
- 一个对象可以同时挂进多个链表，只要嵌多个 `list_head` 成员。
- 通用链表逻辑不关心对象具体类型，类型恢复交给 `container_of`。

驱动里常见的链表用途包括：

- 文件打开后的对象列表。
- 待提交请求队列。
- 已完成请求队列。
- buffer 的 LRU 链表。
- 事件、回调、挂起任务列表。

你读链表相关代码时，不要只盯着 `list_add`、`list_del`。真正应该问的是：

- 这个链表的“拥有者”是谁？
- 节点挂进去意味着对象进入了什么状态？
- 从链表摘下来意味着生命周期发生了什么变化？

也就是说，链表不仅是数据结构，更是在表达状态流转。

### 7. `ops` table 和函数指针表在模拟什么

内核驱动大量使用函数指针表，例如：

```c
struct my_sched_ops {
    int (*submit)(struct my_queue *q, struct my_job *job);
    void (*cancel)(struct my_job *job);
    void (*timeout)(struct my_job *job);
};
```

然后对象里保存一份指向它的指针：

```c
struct my_queue {
    const struct my_sched_ops *ops;
};
```

这个模式的意义很大：

- 调用方不需要知道具体实现细节。
- 不同硬件或不同对象类型可以挂不同实现。
- 公共框架可以定义“接口”，具体驱动去填实现。

这其实就是 C 里的“接口 + 多态”。

在 DRM/GPU 驱动里，这类表非常常见：

- `file_operations`
- 各种 `*_funcs`
- 各种 `*_helper_funcs`
- `vm_ops`
- `dma_fence_ops`

所以当你看到一张函数表时，先别急着逐个函数跳转。先回答两个问题：

- 这一张表是哪个子系统定义的公共接口？
- 当前驱动/对象往这张表里填了哪些自己的行为？

只要把“接口是谁定义的”和“实现是谁提供的”分开，你会清楚很多。

### 8. 从 `ops` 回头看 GPU 驱动为什么像“框架套框架”

GPU 驱动往往不是一个扁平模块，而是多层框架叠起来：

- Linux 设备模型定义一层公共接口。
- DRM core 再定义一层图形设备公共接口。
- KMS 再定义显示对象相关接口。
- GEM/TTM、VM、scheduler、fence 这些子模块还会再各自定义一层接口。
- 具体驱动只是在每一层把自己的对象和函数填进去。

所以很多源码“看起来绕”，其实只是因为：

- 你现在看到的是公共层调用私有层。
- 或者私有层回调公共层。

这也是为什么 Session 02 一定要补对象嵌入和函数指针表。因为后面几乎每个模块都用这一套。

### 9. 指针阅读最重要的不是语法，而是“所有权”和“关系”

很多人一看到多级指针就紧张，但在驱动阅读里，比“指针声明怎么读”更重要的是下面几件事：

- 这个指针指向的是谁拥有的对象？
- 它是长期持有还是临时借用？
- 它可能为空吗？
- 它是否受锁保护？
- 释放时机由谁决定？

比如：

```c
struct my_file {
    struct my_device *mdev;
    struct my_context *ctx;
};
```

这里真正值得问的是：

- `mdev` 是所有文件共享的全局设备，还是每次打开新建的？
- `ctx` 是文件私有上下文吗？
- 文件关闭时是否要释放 `ctx`？

因此读指针字段时，建议你给每个指针贴标签：

- 父对象指针
- 子对象指针
- 借用引用
- 拥有引用
- 回调上下文
- 资源句柄

这样你就不是在“认语法”，而是在恢复对象关系图。

### 10. 生命周期控制：引用计数为什么这么重要

驱动对象往往不会简单地“谁创建谁销毁”，因为：

- 用户态文件可能还持有它。
- 队列里可能还有未完成任务引用它。
- 中断处理或工作队列稍后还会访问它。
- 另一个框架对象可能间接引用它。

所以内核大量使用引用计数，例如 `kref`、`refcount_t`。

你可以先把它理解成一句话：

- 只要还有人可能用这个对象，就不能释放。

这类代码常见形态是：

- 创建时初始引用为 1。
- 谁要跨作用域持有，就增加引用。
- 谁用完，就减少引用。
- 归零时，进入真正的释放路径。

后面你读 GEM object、buffer object、fence、上下文对象时，引用计数几乎是必看字段。

### 11. 并发控制：锁不是附属字段，而是对象语义的一部分

驱动里常见的锁包括：

- `mutex`：适合睡眠上下文的互斥保护。
- `spinlock_t`：适合不能睡眠的短临界区，常见于中断、队列状态。
- `rwlock` / `seqlock` / `ww_mutex`：在特定子系统里处理更复杂的访问模式。

学习这一节时，不要求你一口气掌握所有锁细节，但至少要形成这个意识：

- 每个共享对象都要问“谁在并发访问它”。
- 每次字段读写都要问“这受什么锁保护”。

后面 GPU 驱动里常见的情况包括：

- 提交线程在改队列状态。
- 中断线程在更新完成状态。
- 内存回收路径在扫描对象列表。
- 用户态 `ioctl` 同时在读写同一类资源。

所以一个对象结构体里出现锁，不是“实现细节”，而是在声明这个对象的并发边界。

### 12. 位图、状态位、枚举为什么也很常见

内核代码很喜欢把对象状态压成 bit flags，而不是写成一堆布尔变量。

比如一个请求对象可能有这些状态：

- 已创建
- 已入队
- 已提交
- 已完成
- 超时
- 取消中

用状态位的好处是：

- 节省空间。
- 易于组合状态。
- 易于原子更新。
- 适合和锁、原子变量一起使用。

所以读状态字段时，你需要特别留意：

- 哪些位可以同时存在。
- 哪些状态应该单向流动。
- 哪些状态转换需要加锁。

这会直接影响你后面读 scheduler、fence、hang/reset 路径时的理解。

### 13. 位运算的进阶：不要手写移位，用 `BIT` 和 `GENMASK`

GPU 驱动最底层的部分就是读写硬件寄存器，这无可避免地要操作特定的位（bit）或位域（bitfield）。在普通 C 代码里，你可能习惯写 `(1 << 5)` 或者 `(0xF << 8)`。但在内核里，最常见的是使用标准宏：

- `BIT(5)` 替代 `1 << 5`，增强可读性并防止类型溢出。
- `GENMASK(11, 8)` 用来生成一段连续的掩码（比如第 8 到 11 位全为 1）。

对于超长的状态组合，内核还会提供 `DECLARE_BITMAP` 以及 `set_bit`、`test_bit` 等接口。你在后续阅读寄存器定义头文件（或者 amdgpu/i915 的位域操作）时，满屏都是这些宏。

### 14. 特殊空间修饰符：`__iomem` 与 `__user` 到底是什么

前面的例子中出现过 `void __iomem *mmio;`。内核代码喜欢用“Sparse 注解”这一类修饰符来标记不同特征的地址空间。

- `__iomem`：表示这块内存是物理映射得到的设备 I/O 寄存器。这意味着**绝对不能直接用指针解引用**（例如 `*mmio = 1`），而是必须通过专用的 I/O 访问函数，比如 `readl()`、`writel()`，以保证内存屏障和总线访问的正确性。
- `__user`：表示这个指针来自用户态（比如通过 `ioctl` 传进来的）。内核不能直接信任和访问它，必须通过 `copy_from_user` 才能安全读取，否则会引发严重的安全漏洞或内核崩溃。

当你看到这些修饰符时，不要觉得是用来“占位置的空集”，它们是在大声提醒你“这个地址所在的访问边界不同”。

### 15. 错误处理玄机：指针不仅仅是地址，还可能是错误码

函数出错时，我们通常返回 `NULL` 或者像 `-ENOMEM` 这样的负数错误码。但在内核里经常遇到这种情况：函数既想返回一个有效指针，又想在失败时告诉你是“内存不足”还是“参数错误”，怎么办？

内核巧妙地利用了虚拟地址空间最顶部的几个页（这些非法地址通常不会被真正映射），把它们当作“包含错误码的无效指针”。

因此，你会频繁看到这样的代码：
```c
struct my_obj *obj = create_obj();
if (IS_ERR(obj)) {
    return PTR_ERR(obj); // 将指针转换回实际的负数错误码 (如 -ENOMEM)
}
```
阅读代码时要特别小心：如果你不知道这个约定，看到返回指针直接写 `if (!obj)` 判空，就会漏掉对带有错误码的指针（如 `-ENOMEM` 的伪指针）的拦截。

### 16. 几种最常见的内核对象组织模式

这一节可以先把常见写法压缩成三大类：

#### 模式一：公共基类 + 私有扩展

```c
struct my_bo {
    struct drm_gem_object base;
    struct sg_table *sg;
    size_t size;
};
```

适用场景：

- 接进某个公共子系统。
- 复用公共生命周期或公共接口。
- 在公共对象基础上增加驱动私有状态。

#### 模式二：对象 + 挂接节点

```c
struct my_job {
    struct list_head pending_link;
    struct list_head completed_link;
    struct rb_node timeline_node;
};
```

适用场景：

- 一个对象要出现在多个集合里。
- 同一个对象在不同阶段挂不同管理结构。
- 通过集合来表达调度、生命周期和检索路径。

#### 模式三：对象 + 行为表

```c
struct my_plane {
    const struct my_plane_ops *ops;
};
```

适用场景：

- 公共代码定义接口。
- 多个对象类型复用调用路径。
- 不同硬件或不同对象类型提供不同实现。

后面你读驱动源码时，只要先判断当前对象主要属于哪一种组织模式，很多代码会马上变直观。

### 17. 把这些模式映射到 DRM/GPU 驱动里

下面列几个你后面会不断见到的例子：

- `drm_device`
  代表一张 DRM 设备的公共核心对象，具体驱动会在它外面再包自己的私有设备结构体。

- `drm_crtc`、`drm_plane`、`drm_connector`
  这些是 KMS 公共对象，驱动往往通过私有结构体嵌入它们，再配一张 `funcs`/`helper_funcs` 表。

- `drm_gem_object`
  很多驱动的 buffer object 会在这个基类上继续扩展。

- `dma_fence`
  同步对象的公共基类，具体驱动把它嵌进自己的请求或完成对象里。

- `file_operations`
  字符设备文件接口表，告诉内核打开、映射、`ioctl`、释放分别走哪条函数。

你现在不需要记住所有具体类型，但要记住一种读法：

1. 先找结构体定义。
2. 看它嵌了哪些公共对象。
3. 看它挂了哪些链表/树节点。
4. 看它有哪些锁、引用计数、状态字段。
5. 再看它绑定了哪些 `ops` 或回调。

这个顺序比一上来追函数调用稳定得多。

### 18. 源码阅读时怎么快速拆一个陌生结构体

后面碰到新对象时，可以按下面顺序扫一遍：

1. 看结构体名字和注释，猜它代表什么实体。
2. 先圈出“框架基类成员”，例如 `base`、`drm`、`fence`、`node`。
3. 再圈出资源字段，例如 buffer、寄存器映射、页表、地址空间。
4. 标出同步字段，例如 `mutex`、`spinlock_t`、原子变量、引用计数。
5. 标出行为入口，例如 `ops`、回调、工作项、定时器。
6. 最后再回头追初始化函数、注册函数、释放函数。

如果你反过来做，一上来追调用链，很容易迷路。

### 19. 这一节先记住的关键概念

- `struct`
  在驱动里通常表示一个完整对象，而不是单纯的数据包。

- 对象嵌入
  通过把公共对象或挂接节点放进私有对象内部，接入公共框架或集合。

- `container_of`
  从成员地址反推出完整对象地址，是侵入式数据结构和框架回调的关键工具。

- `list_head`
  内核最常见的双向链表节点，用来把对象挂进各种管理列表。

- `ops` table
  用函数指针表表达接口、多态和框架回调。

- 引用计数
  用来管理对象生命周期，避免对象仍被使用时被提前释放。

- 锁
  用来描述对象在并发环境下的访问边界。

- 位运算宏与特殊修饰符
  学会用 `BIT` 和 `GENMASK` 阅读寄存器操作，理解 `__iomem` 和 `__user` 跨越访问边界的含义。

- 错误指针
  理解 `ERR_PTR` 和 `IS_ERR` 的用法，指针有时不仅是地址，还会携带错误码。

### 20. 学完这一节以后，后面读代码要特别关注什么

从这一节开始，你可以养成一个很值钱的习惯：每看一个对象，都写一行“对象解剖摘要”。

例如：

- 这个对象是谁：某个 BO / 请求 / 显示对象 / 文件私有上下文。
- 它嵌了什么：`drm_gem_object` / `dma_fence` / `list_head`。
- 它怎么被找到：链表、树、句柄表、文件私有数据。
- 它的行为入口是什么：`ops`、回调、工作项。
- 它的生命周期靠什么保护：引用计数、锁、注册/释放路径。

只要能坚持这样看，后面读 `DRM/KMS` 和具体 GPU 驱动时，你会明显感觉“源码终于开始像一套系统，而不是一堆零件”。
